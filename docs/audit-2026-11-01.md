Branch: `NotBhan/tope`
Scope of this pass: Phase A (audit) and the P0 production-reliability items in
Phase D (enquiry persistence, receipt/QR verification, booking-wizard
navigation). The public-content migration (Phases B/C), the UI/UX work
(Phases E/F) and the performance/Lighthouse work (Phases G/H) are **not** done —

## 1. Existing architecture as found

| Concern | Where it actually lived |
| --- | --- |
| Public catalogue + page copy + SEO | Cloudflare D1, read through `src/core/content/d1-client.ts` |
| Public page rendering | Build-time snapshot (`scripts/sync-content.ts` → `content-snapshot/*.json`, inlined via `import.meta.glob`) |
| Page updates | `POST` to the Vercel deploy hook → full rebuild → `scripts/report-publish.ts` |
| Rendering | `output: 'server'`, `@astrojs/vercel@11.0.16`, no ISR. Only detail/legal pages are prerendered |
| Operational data | Split: Neon PostgreSQL (`src/core/operational/*`) **and** per-instance SQLite (`src/core/db.ts`) |
| Media | Filebase S3-compatible (`src/core/storage/*`) |
| Caching | In-process page cache (45 s) + content cache (5 min / 10 s preview) |

Two independent databases were used for operational data with no single owner.
That split is the source of the two reported production failures below.

## 2. Root causes found

### 2.1 Enquiries were written to ephemeral SQLite, verified against Neon

- `src/modules/plan/service.ts` `createEnquiry()` inserted `event_enquiries` and
  `enquiry_line_items` into **SQLite** via `src/core/db.ts`.
- `src/core/operational/enquiry-qr-service.ts` wrote the QR token into **Neon**
  `enquiry_qr_tokens`, carrying the *SQLite* row id into a column whose foreign
  key points at Neon's (never-populated) `event_enquiries`.
- `lookupEnquiry()` then read the enquiry body from **Neon only**, with no
  fallback. `src/core/operational/enquiry-receipt-service.ts` had a one-way
  SQLite fallback that could never resolve a `?token=` lookup.
- The admin dashboard (`src/modules/admin/service.ts`) listed enquiries from
  **SQLite**, while the admin QR scanner read **Neon**.

On Vercel, SQLite lives at `/tmp/data` and is re-seeded per instance, so an
enquiry could succeed, produce a receipt reference, and then be unreachable —
from a different lambda, from the QR scan, and from the admin list. Seeded demo
rows kept appearing in the dashboard, which is exactly the reported symptom.

A second defect made this look intermittent: the receipt service caught lookup
exceptions and reported "not found", so a database outage and a bad reference
were indistinguishable.

### 2.2 Booking wizard: a blocked step was silent

Reproduced in headless Chromium at 390 × 844 against the production build:

```
before click : scrollY 4737, button at viewport top
after click  : error banner at y = -3952 (4,000 px above the viewport)
after settle : scrollY 989, banner still above the fold
```

- The validation banner was rendered at the top of a ~5,500 px form, far from the
  Continue button the visitor pressed.
- The only scroll was a *smooth* one (`styles/base.css` sets
  `scroll-behavior: smooth`), so there was a window in which nothing on screen
  changed — the click looked inert.
- `localStorage.setItem` was called unguarded from the click and input handlers.
  In private mode or with a full quota it threw `QuotaExceededError`; the input
  handler then skipped `schedulePlanRender()`, so the live summary also stopped
  updating.
- Any exception while painting a restored draft happened *before* the event
  listeners were attached, which left the whole wizard inert.

### 2.3 Content delivery

- Public content is only refreshed by a **full rebuild and redeploy**. D1 is a
  network hop from the Vercel function on every preview/cache-miss read.
- `createPublication()` guards concurrency with
  `INSERT … SELECT … WHERE NOT EXISTS`, which is not race-proof under PostgreSQL
  `READ COMMITTED`; there is no partial unique index or advisory lock.
- `/api/internal/publish-report` records any non-empty `contentVersion` without
  checking it matches the active publication's `requested_version`, and compares
  the shared secret with `!==` rather than a constant-time comparison.
- `@astrojs/vercel@11.0.16` does support ISR (`isr`, `bypassToken`), but no route
  uses it and no public HTML response sets cache headers.

### 2.4 Test isolation

`npm test` runs against whatever `.env` contains, which currently means the live
D1 and the live Neon database. The suite writes `content_publications` (and now
would write enquiries) into production.

## 3. Changes made in this pass

### Enquiries — Neon PostgreSQL is now the single authoritative store

- `src/core/operational/service.ts`: added `insertEventEnquiry()` (enquiry +
  line items in **one transaction**, reference retried on a real unique-constraint
  violation rather than a pre-flight `SELECT`), `listEventEnquiriesPage()`,
  `countEventEnquiries()`, `getEventEnquiryWithItems()`.
- `src/modules/plan/service.ts`: `createEnquiry()` is async and commits to Neon.
  A receipt is only returned after the transaction commits.
- `src/modules/plan/module.ts`: awaits it; a persistence failure now returns a
  real 5xx instead of a success payload.
- `src/modules/admin/service.ts` + `handlers/operations.ts`: the admin list,
  detail and status update read/write the same Neon tables.
- `src/core/operational/enquiry-receipt-service.ts`: an unreachable database is
  no longer reported as "not found"; it raises and the receipt page shows
  "Verification temporarily unavailable".
- `src/core/operational/neon-client.ts`: honours `OPERATIONAL_DB_LOCAL_PATH` so
  tests can run against a local file instead of the live database, and converts
  JS booleans for the SQLite fallback.

### Booking wizard

- `src/modules/plan/pages/PlanPage.astro` + `src/styles/wedding.css`: the
  validation banner now sits directly above the step controls.
- `src/client/plan-wizard.ts`: validation scrolls to the offending field with
  `behavior: 'instant'`; draft storage writes are guarded; the restore-and-paint
  sequence is wrapped so the navigation listeners always attach; a failed
  restore falls back to phase 1.

### Verification tooling

- `scripts/verify-enquiry-e2e.ts` (`npm run verify:e2e`) drives the real HTTP
  routes against a running server and checks the database independently.
- `tests/d1-neon.test.ts` no longer touches the live database.

## 5. Outstanding

Not started, and therefore not claimed:

1. **P0 content migration** — D1 → versioned JSON objects in Filebase, manifest,
   rollback, Content Studio rewrite, D1 retirement. The Filebase compatibility
   audit in the brief has to precede the design: the repo currently only uses
   Filebase for media, and the publishing manifest needs conditional writes that
   S3-compatible providers do not all implement identically.
2. **P0 publishing hardening** — the concurrency, version and secret-comparison
   issues in §2.3.
3. **ISR evaluation** — no route uses it today.
4. **P1 UI/UX, mobile, login entry point.**
5. **P1 booking cost estimator and configurable deposits.**
6. **P1 performance investigation and image work.**
7. **P2 Lighthouse.** Needs a Vercel Preview deployment; nothing was measured
   here, so every Lighthouse number remains "not measured".

Known risks carried forward:

- `bookings` has the same split-store defect as enquiries: rows are created in
  SQLite (`src/modules/bookings/service.ts`) but payments read them from Neon
  (`src/core/payment/payment-service.ts`). `updateBookingDepositConfig()`
  dual-writes with swallowed errors. Not addressed here.
- `loadPlanCatalogue()` reads mandaps/stages/equipment from **SQLite**, while the
  public catalogue reads the same concepts from **D1** — two sources of truth for
  the same catalogue. This will matter for the cost estimator, which needs the
  authoritative prices (currently only in D1).
- D1 `site_settings` currently contains seeded-looking copy in production
  (`"Premier Test Wedding Decorators - 1793451852977"`), which renders in the
  footer.
- `npm test` still writes to the live Neon database for other suites
  (`publication.test.ts`).
